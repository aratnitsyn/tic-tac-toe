## Purpose

Описывает конечный автомат участия игрока в первой версии PvP и отделяет его от соединения и сессии авторизации.

**Состояния:** `MENU`, `LOBBY`, `QUEUED`, `IN_MATCH`. Начальное состояние участия свободного авторизованного игрока — `MENU`; конечного состояния нет.

```text
MENU <--> LOBBY --> IN_MATCH --> MENU
  |                  |
  +<-> QUEUED -------+--> QUEUED / LOBBY
                           cancellation return
```

| Откуда | Событие / условие | Куда | Эффект |
|---|---|---|---|
| MENU | Создание лобби или успешный вход по коду | LOBBY | Занять место в лобби |
| MENU | Вход в поиск | QUEUED | Получить FIFO-приоритет |
| LOBBY | Формирование пары после входа второго игрока | IN_MATCH | Начать проверку готовности |
| QUEUED | Выбор пары | IN_MATCH | Исключить из доступного подбора |
| QUEUED | Успешная отмена поиска | MENU | Удалить доступность для подбора |
| LOBBY | Выход из ожидающей комнаты | MENU | Освободить место |
| IN_MATCH | Отключение в WAITING_READY | MENU / QUEUED / LOBBY | Отключённый в меню, подключённый по источнику |
| IN_MATCH | Оба отключены в COUNTDOWN | MENU | Для обоих без поиска |
| IN_MATCH | Истёк срок готовности, игрок не подтвердил | MENU | Освободить участие |
| IN_MATCH | Игрок подтвердил, соперник не подтвердил | QUEUED / LOBBY | Вернуть по источнику; сохранить FIFO-приоритет |
| IN_MATCH | Соперник отключился во время отсчёта; игрок подключён | QUEUED / LOBBY | Вернуть по источнику; сохранить FIFO-приоритет |
| IN_MATCH | Сам игрок отключился во время отсчёта | MENU | Отменить участие |
| IN_MATCH | Партия завершена | MENU | Освободить участие без автоматического поиска |
| IN_MATCH | Пауза, ход или восстановление во время партии | IN_MATCH | Обновить партию, сохранив участие |

`QUEUED / LOBBY` означает выбор одного состояния по источнику конкретного матча. При возврате в лобби прежняя готовность сбрасывается.

Соединение является независимым измерением состояния:

```text
CONNECTED --> DISCONNECTED --> CONNECTED
```

Отключение не означает выход из аккаунта и не всегда меняет участие. Восстановление соединения само по себе не создаёт новую сессию или новый матч. Автомат сессии авторизации не входит в этот автомат.

## ADDED Requirements

### Requirement: Exclusive player state machine
Система SHALL поддерживать для игрока одно из состояний MENU, LOBBY, QUEUED, IN_MATCH и выполнять согласованные переходы по таблице автомата. Подготовка и пауза матча сохраняют IN_MATCH. Несогласованные переходы не считаются разрешёнными этим контрактом.

#### Scenario: Queue to match
- **WHEN** игрок в QUEUED выбран в пару
- **THEN** он переходит в IN_MATCH и становится недоступен для другого подбора

#### Scenario: Lobby to match
- **WHEN** в приватном лобби образована пара
- **THEN** оба участника переходят из LOBBY в IN_MATCH на проверку готовности

### Requirement: Cancellation routing by participant
При отмене подготовки система SHALL выбирать состояние каждого участника отдельно: не подтвердившему либо отключившемуся во время отсчёта — MENU; подтвердившему при тайм-ауте либо оставшемуся подключённым при отмене отсчёта — исходное LOBBY или QUEUED с прежним приоритетом.

#### Scenario: Matchmaking participant retains priority
- **WHEN** A подтвердил готовность, B не подтвердил, матч пришёл из поиска
- **THEN** A возвращается в QUEUED с прежним приоритетом, B — в MENU

#### Scenario: Lobby participant stays
- **WHEN** матч пришёл из лобби и соперник отключился во время отсчёта
- **THEN** подключённый игрок возвращается в LOBBY, отключившийся — в MENU

### Requirement: Completion and reconnection participation
Система SHALL переводить обоих игроков в MENU после завершения партии. Переподключение SHALL восстанавливать текущее участие: IN_MATCH для незавершённого матча или MENU после его завершения, независимо от устаревшего клиентского состояния.

#### Scenario: Game ended while client was offline
- **WHEN** клиент восстанавливает связь после завершения матча
- **THEN** он получает участие MENU и не возвращается в завершённый матч как активный участник

### Requirement: Conflicting participation transitions
Система SHALL не допускать двойного участия при конкурирующих или повторных командах. Отклонённая команда не изменяет состояние, а повтор одной принятой операции не выполняет переход второй раз.

#### Scenario: Simultaneous lobby and queue requests
- **WHEN** игрок из MENU одновременно запрашивает вход в лобби и поиск
- **THEN** успешен не более одного перехода, игрок не оказывается в обоих состояниях

### Requirement: Additional participation transitions
Система SHALL поддерживать QUEUED → MENU при успешной отмене поиска и LOBBY → MENU при выходе из ожидающей комнаты. Отключение в WAITING_READY возвращает отключённого в MENU, подключённого — по источнику. При отключении обоих в COUNTDOWN оба переходят в MENU.

#### Scenario: Waiting player cancels search
- **WHEN** отмена поиска применяется до закрепления игрока за матчем
- **THEN** игрок переходит из QUEUED в MENU

#### Scenario: Both leave countdown through disconnect
- **WHEN** оба признаны отключёнными во время COUNTDOWN
- **THEN** оба переходят из IN_MATCH в MENU без нового поиска
