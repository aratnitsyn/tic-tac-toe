# Design

## Context

Мотивация и объём — в proposal.md. Репозиторий содержит только AGENTS.md, README и OpenSpec: исполняемых сервисов, клиентов, сборок и инфраструктуры нет. Существующие 11 спецификаций, включая три автомата, являются исходным контрактом. Дизайн необходим из-за межсервисной координации, временных ограничений и конкурирующих команд.

Подтверждённые дополнения к переходам внесены в спецификации. Приведённые ниже технические настройки — решения данного плана, а не результаты измерений. Вместимость 100 000 ещё не подтверждена испытаниями; предварительные SLO из proposal.md не являются утверждёнными критериями.

## Goals / Non-Goals

**Goals:**

- Обеспечить одного владельца каждого инварианта и восстановление после частичного выполнения межсервисных операций.
- Сохранять подтверждённые команды, игровые сроки и FIFO-приоритет независимо от экземпляра приложения.
- Разделить транспорт событий и авторитетное состояние; обеспечить одинаковое поведение трёх клиентов.
- Подготовить воспроизводимые сборки, интеграционные проверки, запуск в Kubernetes и нагрузочный стенд.

**Non-Goals:**

- Глобальные распределённые транзакции, полное event sourcing и заявленная end-to-end exactly-once доставка.
- Несколько регионов с активной записью, независимое шардирование единой FIFO-очереди и полная защита от отказа всего кластера в первой реализации.
- Расширение продуктового объёма: см. исключения proposal.md. User service не добавляет редактирование профиля, рейтинги или пользовательскую историю сверх согласованных требований.

## Decisions

### 1. Сервисы и владельцы данных

Монорепозиторий, независимо собираемые и развёртываемые приложения. Kotlin/Spring Boot: API Gateway, Auth, User, Lobby и Game. Для всех JVM backend сервисов обязательны JDK 25 при сборке и запуске и JVM target 25. Spring Boot — последний стабильный patch ветки 3.5.x, сейчас закреплён 3.5.16; Kotlin — 2.3.21. Динамические зависимости `3.5.+` не используются; patch обновляется согласованно во всех сервисах после проверки. Go: Matchmaking и Realtime. Kotlin объединяет транзакционную доменную логику, Go используется для очереди и большого числа соединений. Альтернатива — один язык; она проще операционно, но не использует выбранный пользователем стек Kotlin/Go.

| Компонент | Авторитетные данные / ответственность |
|---|---|
| Auth | Аккаунт, email, password hash, идентичности, единственная сессия, операции выхода |
| User | Минимальный профиль по userId; идемпотентное создание по AccountRegistered |
| Lobby | Метаданные комнаты, код, доступность комнаты; оркестрация входа |
| Matchmaking | FIFO tickets, исходный приоритет, сохраняемая операция передачи пары |
| Game | Реестр участия игроков, резервирование мест лобби, матч и готовность, партия, сроки, результаты |
| Realtime | Живые соединения, поколения соединений, доставка, наблюдение доступности; не правила победы |
| API Gateway | Аутентификация внешних HTTP-запросов, маршрутизация и ограничения трафика |

Game включает отдельный прикладной модуль координации участия. Только он меняет авторитетное MENU/LOBBY/QUEUED/IN_MATCH; User не хранит второй изменяемый флаг занятости. Это сознательное расширение Game: переходы партии, матча и освобождение обоих участников могут фиксироваться одной транзакцией. Альтернатива — самостоятельный coordinator и saga для каждого завершения; она усложняет критический инвариант без необходимости для первой версии.

У каждого доменного сервиса собственная PostgreSQL database и роль; допустим общий физический кластер стенда. Запрещены межсервисные SQL-запросы и запись в чужие таблицы. Game хранит ссылки и версии, но не копирует пароль или профиль. Redis — ограничение частоты, WS tickets и временная маршрутизация, не источник состояния партий или FIFO. Полная потеря Redis не освобождает игрока от активного матча.

### 2. Внешние маршруты и контракты

```text
Web / iOS / Android
        |
        v
Istio Ingress Gateway (TLS termination)
        |                         |
        v                         v
Spring Cloud API Gateway     Realtime (internal WS)
        |                         |
        v                         v
Auth / User / Lobby / Matchmaking / Game
        |                         |
        +----> PostgreSQL <-------+
                   |
             transactional outbox
                   |
                   v
             NATS JetStream --> Realtime dispatch --> local sockets
```

HTTPS API `https://<host>/api/v1/**` проходит через Spring Cloud Gateway. WebSocket использует точный маршрут `wss://<host>/wss`, который направляется из Istio ingress gateway прямо в Realtime: долгоживущие соединения не проходят через второй proxy. Старый маршрут `/realtime` не предоставляется; `/wss` — путь endpoint, WSS — защищённый протокол. Realtime независимо проверяет доступ. HTTPS-команды, включая ход, отправляются через gateway; WSS — события, heartbeat и управление подпиской. Sticky sessions не требуются: после переподключения клиент может попасть в другой pod.

Backend разворачивается в Kubernetes с Istio service mesh в sidecar-режиме. Istio ingress gateway — отдельный Deployment с pod-ами gateway-прокси Envoy и Kubernetes Service; это исполняемый компонент, а не только ресурс маршрутизации. Istio Gateway задаёт listeners/TLS, VirtualService — маршруты: prefix /api/v1/ к Spring Cloud API Gateway и exact /wss к Realtime с WebSocket upgrade. Для /api/v1 отдельно не вводится endpoint без завершающего слеша. Ingress gateway заменяет ранее запланированный NGINX Gateway Fabric: второго L7 ingress в этой схеме нет. Spring Cloud API Gateway остаётся прикладным gateway аутентификации и маршрутизации API.

Граница шифрования: клиент → ingress использует HTTPS/WSS с проверкой сертификата; на ingress выполняется TLS termination. Далее ingress → backend и вызовы сервисов внутри mesh используют HTTP, а WebSocket — WS по тому же пути /wss. TLS повторно на этих участках не устанавливается. Внешний HTTP/WS доступ и fallback клиента на cleartext запрещены; внутренний HTTP/WS является штатным транспортом.

По требованию проекта внутри mesh нет ни application TLS, ни proxy-to-proxy mTLS. Для backend namespace настраивается PeerAuthentication DISABLE, а для mesh-upstreams — DestinationRule с tls.mode DISABLE, включая маршруты ingress и egress, чтобы auto-mTLS не добавлял шифрование. Нельзя полагаться только на HTTP URL приложения или PERMISSIVE: они не означают отсутствие mTLS между proxy. Проверки Envoy config и сетевой трассы подтверждают фактический plaintext. Backend остаётся закрытым от внешнего прямого доступа; используются NetworkPolicy, отдельные роли и сервисная авторизация. Без mTLS не следует рассчитывать на криптографически подтверждённый Istio source principal; доверенные внутренние вызовы требуют прикладных credentials.

Исходящий HTTP-трафик к внешним системам проходит через отдельный Istio egress gateway: mesh → egress по HTTP, egress → внешний HTTPS endpoint по TLS с проверкой CA/имени узла. Здесь выполняется TLS origination, а не termination входящего клиентского HTTPS. ServiceEntry, VirtualService и DestinationRule описывают разрешённые назначения; NetworkPolicy/сетевые ограничения закрывают обход egress, одной настройки REGISTRY_ONLY недостаточно как сетевой изоляции. В v1 нет внешних auth/email интеграций: egress проверяется на контролируемом тестовом endpoint.

PostgreSQL, Redis и NATS на стенде размещаются внутри кластерной доверенной сети и используют собственные TCP-протоколы без дополнительного TLS; они не становятся HTTP-сервисами из-за наличия mesh. Для них задаётся корректная классификация TCP портов и отдельные NetworkPolicy/credentials. Их перенос за пределы доверенной сети потребует отдельной настройки транспорта: HTTP TLS origination нельзя автоматически применять к произвольному DB-протоколу. Healthchecks используют внутренний HTTP либо exec probes. Сертификаты нужны на внешних границах ingress/egress, а не каждому backend приложению.

Контракты OpenAPI для HTTP и AsyncAPI/JSON Schema для событий хранятся в `contracts/`, проверяются на совместимость и используются клиентами. Базовый набор операций:

| Область | Операции |
|---|---|
| Auth | register, login, logout, session, issue-ws-ticket |
| Participation | получить актуальное участие и ссылку на текущий матч |
| Lobby | создать, присоединиться по коду, получить свою комнату, покинуть ожидающую комнату |
| Matchmaking | вступить в очередь, отменить поиск, получить свой ticket |
| Match | получить snapshot, подтвердить готовность |
| Game | получить snapshot, сделать ход, сдаться |

Изменяющая команда содержит commandId/Idempotency-Key, а для существующего агрегата — expectedVersion. Ключ дедупликации scoped по userId и типу операции; сохраняются hash payload и результат. Другой payload с тем же ключом отклоняется. Результаты команд матча сохраняются вместе с матчем; не зависят от короткого окна дедупликации брокера. Другие команды сохраняются минимум 24 часа, после срока клиент сверяет snapshot вместо слепого повтора.

Ответ содержит serverTime, версию и результат операции. Стабильные ошибки: UNAUTHENTICATED, SESSION_ALREADY_ACTIVE, PARTICIPATION_CONFLICT, VERSION_CONFLICT, DEADLINE_EXCEEDED, INVALID_MOVE, LOBBY_UNAVAILABLE, RATE_LIMITED. При конфликте версии клиент сначала получает snapshot. HTTP timeout не означает отмену уже принятой команды; повторяется тот же commandId.

### 3. Аккаунт и единственная сессия

Auth хранит неизменяемый userId, emailOriginal, emailKey, emailVerifiedAt и credential с версией hash. Техническая политика v1: trim email, ASCII local part и домен, проверка структурным валидатором, case-insensitive emailKey, уникальный индекс; точки и plus-суффиксы не удаляются. Это политика идентификатора нашего продукта, а не утверждение о правилах каждого почтового сервера. Она фиксируется в контракте и тестах. Проверка существования адреса и отправка писем отсутствуют.

Пароль не нормализуется; состав и длина строго из account-access. Argon2id с индивидуальной солью и сохранением параметров; начальные параметры не ниже актуального минимума OWASP, затем benchmark на целевом Auth pod. Пользовательский лимит 6–15 не меняется этим дизайном. Перед проверкой hash действуют rate limits по источнику и аккаунту.

Выбран непрозрачный случайный session token; в session slot хранится только его hash. Для идемпотентного повтора login отдельно хранится зашифрованный ответ на 24 часа от создания, без продления при чтении. AES-256-GCM использует новый случайный nonce и authenticated context операции; keyId указывает на ключ вне БД (Vault; Kubernetes Secret допустим только как автоматически синхронизируемая копия для потребителя). Открытый token не попадает в command_results, события и логи. Повтор login после logout/истечения сессии не восстанавливает её. По истечении 24 часов ciphertext удаляется; старые ключи доступны только до истечения связанных ответов. Решение согласовано пользователем. Одна строка session slot на accountId под блокировкой: проверка срока и создание сессии атомарны. Активная сессия даёт SESSION_ALREADY_ACTIVE после проверки учётных данных. Авторизованная introspection обновляет lastActivity; срок — lastActivity +24 часа. Равенство сроку означает истечение. Heartbeat и фоновые авторизованные обращения считаются активностью. В первой реализации Auth проверяет PostgreSQL без положительного кеша сессии; Redis не определяет её действительность.

Spring Security использует opaque token introspection. Native-клиенты хранят токен в системном защищённом хранилище; Web — в Secure HttpOnly SameSite cookie с CSRF-защитой изменяющих запросов и проверкой Origin. Секреты не попадают в URL/логи. Внешние провайдеры позднее добавляются как identity(provider, subject, userId) с уникальностью provider+subject; их реализация и объединение аккаунтов не входят в v1.

Выход — сохраняемая операция Auth: сначала перевод session в CLOSING, блокировка новых обычных обращений и выдачи WS tickets, затем внутренний LogoutParticipation в Game. Game под блокировкой приводит уже завершённую партию к тому же результату либо фиксирует SURRENDER; во время подготовки отменяет её с освобождением выходящего. Только после подтверждения Game Auth завершает session. При сбое операция повторяется; другой вход не открывается до завершения CLOSING. Уже авторизованные конкурирующие команды могут линеаризоваться перед сдачей, но не менять терминальный результат. Потеря session token без выхода требует дождаться 24 часов: обход единственной сессии не добавляется.

### 4. Реестр участия и Lobby

Game хранит participation(userId PK, state, resourceId, version, operationId), room_slots(roomId, userId, slot) и match members. Переходы MENU→LOBBY/QUEUED и резервирование пары выполняются только через его API с блокировками пользователей в порядке userId. Ограничения БД и проверки версии запрещают двойное назначение. На пользователя допускается одна незавершённая операция координации; её внутренний статус не создаёт пятое публичное состояние участия.

Lobby сначала сохраняет комнату как недоступную с operationId, затем идемпотентно регистрирует ресурс и место создателя в Game. После подтверждения открывает код. Game является владельцем занятых слотов и проверяет существование активной регистрации комнаты, вместимость и участие. Lobby не принимает решение по устаревшей проекции. Присоединение второго игрока в Game одной транзакцией переводит обоих в IN_MATCH и создаёт WAITING_READY. Результат возвращается через Lobby; потеря ответа восстанавливается по operationId.

Код: 10 случайных символов из uppercase алфавита без неоднозначных знаков, уникальный индекс с повторной генерацией при коллизии. Код действует, пока комната ожидает приглашённого; нет автоматического истечения с пользовательским эффектом в v1. После отмены подготовки для оставшегося игрока код ротируется и снова открывается. Если никто не вернулся, комната закрывается; при завершении сыгранной партии оба уходят в меню, старый код недействителен. Выход единственного участника закрывает комнату. Выход проигрывает гонку с формированием пары, если участие уже IN_MATCH, и не освобождает активного игрока.

Межсервисные уведомления закрытия могут запаздывать: Game проверяет регистрацию/занятость ресурса при каждом join; недействительная ссылка в Lobby не создаёт матч. Компенсация по timeout не освобождает участие, пока результат операции Game неизвестен; reconciler запрашивает operationId. Это медленнее общей транзакции БД, но сохраняет независимость сервисов и инварианты.

### 5. FIFO и передача пары

Matchmaking хранит tickets(userId unique, admissionSequence, originalSequence, participationVersion, status, operationId) и singleton queue_control. Новый поиск сначала закрепляет QUEUED через Game. После этого транзакция Matchmaking под блокировкой queue_control присваивает монотонный admissionSequence и подтверждает вход клиенту. Это серверный момент входа в очередь; порядок arrival на разных gateway не обещается. При сбое между стадиями outbox/reconciler завершает admission либо компенсирует ещё не переданное участие по версии.

Все операции, изменяющие доступный порядок FIFO, коротко сериализуются на queue_control. Выбираются два первых AVAILABLE по originalSequence; им атомарно назначаются один pairOperationId и RESERVED. Несколько HTTP pods допустимы, но решение о следующей паре сериализовано. SKIP LOCKED для обхода головы очереди не используется; он допустим для независимых фоновых задач, не для строгого порядка игроков.

Game получает AssignPair с обоими userId, ожидаемыми версиями QUEUED, ticket ids и matchId. Одной транзакцией проверяет участие, создаёт матч и закрепляет обоих. Повтор по pairOperationId возвращает тот же matchId. После подтверждения Matchmaking помечает tickets CONSUMED. При неизвестном исходе RESERVED не освобождаются по времени: сначала запрос результата в Game. При отказе CAS выполняется сверка обоих участников, действительный ticket возвращается с исходным приоритетом.

Отмена поиска и AssignPair конкурируют на реестре Game. Если победила отмена, назначение не проходит CAS; если победило назначение, cancel возвращает PARTICIPATION_CONFLICT и текущий матч. Нет скрытой сдачи. Временные разрывы saga не делают игрока доступным одновременно другому способу подбора.

При отмене подготовки Game возвращает подходящего игрока в QUEUED и публикует ReturnToQueue с originalSequence. Matchmaking идемпотентно делает ticket AVAILABLE. Приоритет применяется среди доступных игроков при следующем выборе; уже закреплённые пары не вытесняются. Технически недоступный или отключённый ticket не обгоняет голову: его сначала сверяют и удаляют/приостанавливают, затем продолжают выбор. Глобальную очередь не шардируем: шардирование изменило бы строгий FIFO. Узкое место измеряется отдельно.

### 6. Матч, партия и транзакции

Game хранит match(id, source, sourceRef, status, readyA/B, readyDeadline, startDeadline, version), game(matchId unique, board, status, turn, turnDeadline, remainingTurn, recoveryA/B, result, version), deadlines, command_results и outbox. Подготовка и партия используют одну PostgreSQL database, но разделены доменными модулями.

Одна команда: проверить session/права → открыть транзакцию → заблокировать агрегат и необходимые participation строки → сначала применить уже наступившие сроки → проверить expectedVersion и правила → сохранить изменения, результат команды и outbox → commit → ответ. Временная точка проверки определяется PostgreSQL clock_timestamp после получения блокировки, а не временем клиента или приёма на gateway. Ограниченные lock timeout и размер транзакций предотвращают бесконечное ожидание.

После обоих подтверждений устанавливается startDeadline; после него Game атомарно создаёт партию и переводит матч в RUNNING. Равенство readyDeadline уже опоздало. На старте и после незавершающего хода новый срок — serverNow +5 секунд. При завершении партия FINISHED, матч FINISHED и участие обоих MENU фиксируются вместе. Случайное назначение символов выполняется один раз и сохраняется.

Отключение в WAITING_READY отменяет подготовку, подключённый возвращается по источнику без требования уже подтвердить. В COUNTDOWN отключение отменяет подготовку; если оба отключены, оба возвращаются в MENU. Если второе отключение наблюдалось после первой отмены, обработчик также снимает ещё не потреблённый автоматический возврат; если игрок уже вошёл в новый матч, событие старого матча не меняет новый. Все события адресованы matchId и generation, не только userId.

### 7. Таймеры и обнаружение отключения

Надёжный источник сроков — PostgreSQL. Индексированные due deadlines обрабатывают несколько workers с коротким захватом задач; просроченная задача повторяется после crash. Перед применением проверяются matchId, deadline kind, generation и актуальная версия. Локальный scheduler ускоряет обработку, но не является источником истины. Удаление старой задачи не отменяет проверку срока на каждой команде.

Game сравнивает все наступившие события и применяет самое раннее по сохранённому effective deadline, не по порядку запуска workers. При равных recovery deadlines обоих — BOTH_DISCONNECTED_TIMEOUT; равенство сроку не позволяет ход или восстановление. Сначала проверяется наступивший срок, затем команда. Необработанный вовремя timer не даёт дополнительного времени.

Realtime использует application heartbeat каждые 2 секунды и lease 6 секунд как стартовые настройки стенда. TCP close даёт немедленное наблюдение, молчание — после lease. До признания отключённым таймер хода продолжает идти; 30 секунд отсчитываются от серверного обнаружения. Числа heartbeat — техническая конфигурация, должны проверяться на мобильной сети и пересматриваться без изменения правила 30 секунд.

Game хранит durable connection generation и lease только для игроков подготовки/матча; heartbeat меню не создаёт строку записи Game. Смена поколения при переподключении fence-ит старый socket. Периодические продления для игроков активных матчей сохраняются пакетно с серверным временем; отсутствие renew после падения Realtime pod превращается в disconnect по сохранённому lease. Пока renew для текущего поколения не подтверждён, Realtime не обещает клиенту CONNECTED. Redis ownership помогает маршрутизировать, но его потеря не стирает сохранённый срок.

При паузе фиксируются turn и max(0, turnDeadline − serverNow), disconnectedAt и recoveryDeadline каждого отсутствующего. При восстановлении до срока остаток recovery уменьшается на длительность отсутствия; у подключённого запас не расходуется. Возобновление возможно только при обоих подключённых и даёт новый turnDeadline = serverNow + remainingTurn. Истёкший ранее turnDeadline нельзя превратить в паузу задним числом. Часы для доменных сроков берутся из Game DB; application monotonic clock используется только для ожиданий и UI.

Массовый инфраструктурный сбой не создаёт автоматического исключения правил поражения в v1. Это явный риск учебного стенда: результаты при падении LB/Realtime проверяются и наблюдаются, а не маскируются остановкой таймеров. Политика аварийной отмены матчей потребует отдельного изменения требований.

### 8. События и Realtime

Каждый владелец данных записывает outbox в транзакции изменения. Publisher отправляет в JetStream с eventId, ждёт publish ack и только затем отмечает публикацию. Consumer фиксирует inbox(eventId unique) вместе с эффектом и подтверждает сообщение после commit. Backoff, max attempts и отдельный parking stream сохраняют неисправные сообщения для разбора. Ограниченное окно broker dedup не заменяет inbox.

Envelope: eventId, type, schemaVersion, aggregateId, aggregateVersion, occurredAt, correlationId, causationId и payload без секретов. События агрегата применяются по версии; consumer не предполагает глобальный порядок между сервисами. Первый вариант stream — limits retention, три реплики на нагрузочном кластере; локальный стенд может использовать одну. Retention и disk limits задаются явно в конфигурации, lag и исчерпание лимита — алерты.

Realtime состоит из socket pods и dispatcher workers в одном сервисе с разными deployment roles. Durable pull consumer распределяет работу dispatchers; событие раскладывается по адресатам. По Redis ownership userId→podId/generation отправляется best-effort сообщение в адресный Core NATS subject pod. Нельзя использовать один общий queue group socket pods: событие могло бы попасть pod без нужного клиента. Потеря ownership означает обязательную синхронизацию клиента, не потерю авторитетной команды.

После внешнего WSS upgrade (внутри mesh — WS) клиент передаёт короткоживущий одноразовый ticket в первом auth frame; до успешной проверки подписки и события запрещены. Ticket выдаёт Auth через авторизованный HTTP, срок 30 секунд, atomic consume в Redis. Долгоживущий токен не помещается в URL. Проверяются Origin Web, session, участник матча и generation. Смена соединения внутри той же сессии не создаёт вторую сессию; старое соединение закрывается после fencing.

Доставка в сокет не означает получение клиентом. Клиент применяет версии, подтверждает события; на gap, timeout ack, reconnect, foreground resume и каждые 5 секунд выполняет сверку snapshot/version. Сначала подписка, затем snapshot и обработка буфера событий новее snapshot. Это закрывает окно гонки подписки и чтения. Ограниченные outbound buffers: медленный клиент получает resync-required или disconnect; не блокирует общий dispatcher. Результат хода доступен и в HTTP-ответе, независимо от WS.

Для этапов 10.5–10.6 пользователь согласовал сервер и тестовый Go-клиент
синхронизации (`services/realtime/internal/syncclient`): subscribe barrier через
resync_required, HTTP snapshots с буфером, ack, сверка каждые 5 секунд,
foreground и reconnect с новым ticket той же сессии. Реализация интерфейсов
Web/iOS/Android остаётся в этапах 11–13. Тестовый клиент получает authority
snapshot при каждой новой версии; это корректный начальный алгоритм, стоимость
дополнительных HTTP чтений учитывается при последующих нагрузочных испытаниях.

### 9. Структура реализации и качество

Планируемая, пока не существующая структура:

```text

web/                               # React/TypeScript (корень по решению пользователя)
clients/{ios,android}/
contracts/{http,events}/
infra/{local,kubernetes}/
tests/{integration,e2e,load}/
docs/{runbooks,performance}/
```

Для запуска Gradle на JDK 25 требуется Gradle 9.1+. В scaffold закреплён официальный Wrapper 9.8.1 с SHA-256; чистые сборки всех пяти JVM-сервисов на JDK 25 успешно выполнены. Документация Boot 3.5 перечисляет Gradle 7/8, поэтому это результат проверки конкретной комбинации, а не расширение официальной матрицы поддержки. Сборка выдаёт предупреждения об устаревающих API плагинов перед Gradle 10. CLI линтеров изолированы от dependency management приложения через executable JAR.

В Kotlin — Gradle wrapper и зафиксированные toolchains, ktlint/detekt; Go — go.mod/go.sum, gofmt/go vet/golangci-lint; Web — lockfile, ESLint/Prettier; iOS — SwiftFormat/SwiftLint; Android — Gradle wrapper, ktlint/detekt. Точные совместимые версии фиксируются при scaffold в manifests, без плавающих latest. JSON-контракты не делят доменные классы между сервисами. Локальные проверки документируются только после появления исполняемых команд.

Тестирование: правила и автоматы на управляемом времени; PostgreSQL integration tests реальных блокировок/unique constraints; fault injection между commit, publish и ack; контрактные проверки трёх клиентов; e2e через gateway и WSS. Не использовать sleep для проверки дедлайнов там, где доступен fake clock. Авторитетное время в интеграционном тесте согласуется с DB.

### 9.1. Helm, YAML, Vault и конфигурация Kubernetes

Доступный Kubernetes-кластер является предварительным условием. Helm устанавливает и обновляет инфраструктуру и приложения внутри кластера; создание узлов/control plane остаётся задачей окружения (для текущего стенда — Docker Desktop). Версии Helm, charts и образов закрепляются; установка, обновление и rollback документируются и проверяются. Rollback релиза не откатывает автоматически данные и миграции БД.

Kubernetes и Istio имеют отдельные charts/каталоги и отдельные YAML templates и values. Kubernetes-часть содержит workloads, Service, ServiceAccount/RBAC, ConfigMap, NetworkPolicy и storage; Istio-часть — Gateway, VirtualService, DestinationRule, PeerAuthentication и ServiceEntry. Обе части устанавливаются через Helm в документированном порядке зависимостей. JSON manifests/values и Python-генерация инфраструктурных manifests заменяются YAML-источниками и Helm templates. Ограничение формата не относится к JSON API-контрактам приложений.

Все несекретные параметры приложений, включая адреса, порты, origins, таймеры и настройки пулов, передаются через ConfigMap с envFrom/configMapKeyRef либо смонтированным файлом. Helm values параметризуют эти ConfigMap и Kubernetes/Istio ресурсы; секретных значений в values и ConfigMap нет. Изменение конфигурации применяется через rollout или поддержанный механизм перезагрузки с проверкой фактического значения в приложении.

Vault — единый источник инфраструктурных секретов, credentials, ключей шифрования login-ответов и TLS-материалов (сертификаты, закрытые ключи, CA/trust bundles) Kubernetes-окружения. Пароли пользователей остаются hash в Auth DB, а session token — hash/зашифрованный login-ответ по §3; Vault не заменяет доменные хранилища. Интеграция Kubernetes аутентифицируется в Vault через Kubernetes ServiceAccount с привязкой к namespace и минимальным policy; постоянный root token не передаётся workloads. Kubernetes Secret разрешён только как автоматически синхронизируемая из Vault копия для потребителей, которым он необходим, включая ingress TLS. Остальные потребители могут получать материалы через mount. Конкретный совместимый механизм интеграции, версии и runbook фиксируются при реализации.

Секреты и TLS-материалы не генерируются deployment-скриптом в локальном credential-файле и не передаются в Helm values, Git или логи. Первичная загрузка/миграция существующих credentials в Vault выполняется без потери доступа к действующим БД и ключей ранее зашифрованных login-ответов. Bootstrap/unseal/recovery Vault описывается отдельно; bootstrap credentials не становятся секретами приложения. Обновление и ротация в Vault должны доходить до потребителей; порядок смены паролей согласуется с хранилищем. При недоступности Vault новый workload без обязательных материалов не становится ready; работающий использует только ещё действующие материалы по документированной политике, без fallback к локальным файлам. Доступ к Vault и его аутентификации разрешается сетевыми политиками. Правило plaintext для игровых HTTP/WS и TCP-хранилищ не отменяет проверку TLS при защищённом доступе к Vault.

Межсервисная HTTP/WS-маршрутизация явно описывается mesh VirtualService и DestinationRule для соответствующих FQDN/портов; ingress и egress имеют отдельные ресурсы/scopes. Kubernetes Service обеспечивает discovery/endpoints, Spring Cloud API Gateway сохраняет прикладную аутентификацию и API-маршрутизацию. Для PostgreSQL/Redis/NATS задаются TCP-порты и необходимые DestinationRule; HTTP rewrite к ним не применяется. PeerAuthentication/DestinationRule DISABLE из §2 сохраняются; NetworkPolicy ограничивает соединения независимо от Istio-маршрутов.

Текущая реализация 14.1 (JSON manifests, Python renderer и локальные credential/certificate файлы) проверена по прежнему плану и требует миграции. Прежний отчёт не подтверждает требования Helm/Vault/YAML. Локальный Compose и local.env не изменяются этой корректировкой Kubernetes-плана.

### 10. Нагрузка, эксплуатация и границы приёмки

Стартовый воспроизводимый профиль стенда: 20 000 в меню, 10 000 в ожидающих лобби, 10 000 в очереди, 10 000 в подготовке и 50 000 в играх (25 000 партий). Это проектный профиль испытания, а не обещанное продуктовое распределение. Боты генератора поддерживают доли через контролируемую скорость входа/подбора и подтверждения. Отдельно — до 50 000 PvP-партий и всплески поиска/переподключения в пределах общего лимита.

Предположение для расчёта: средний интервал хода 2 секунды даёт примерно 12 500 ходов/с для 25 000 партий, не считая таймеров, подписок и новых матчей. 100 000 клиентов с heartbeat каждые 2 секунды дают около 50 000 heartbeat/с; snapshot каждые 5 секунд добавляет до 20 000 сверок/с. Это расчёт нагрузки, не результат benchmark. Бюджеты Auth introspection и durable leases включаются отдельно: нельзя считать только ходы.

Нагрузочный прогон: ступени 1k/10k/50k/100k, разогрев 10 минут и плато 30 минут для каждого выбранного профиля. Записываются ресурсы pods/DB/Redis/NATS, параметры пулов, RTT, фактические доли, throughput, p50/p95/p99, ошибки, event lag, timer lag, lock waits, FIFO violations и двойные назначения. Zero violations обязательны для инвариантов; предварительные latency SLO измеряются как ориентиры, не как уже согласованный pass/fail.

Для приёмки реализации необходимы рабочие сценарии всех клиентов, проверки инвариантов и воспроизводимый отчёт. Цель 100k нельзя объявить достигнутой, если не поддержан профиль или растёт backlog. Ресурсный бюджет, верхние пороги ошибок/задержек и месячный SLO требуют отдельного утверждения до объявления полной приёмки НФТ; это не блокирует создание инструментов и функциональную реализацию.

Kubernetes с Istio: отдельные ingress/egress gateway deployments, sidecars backend, readiness/liveness, resource requests/limits, несколько replicas stateless сервисов, ограничения connection pools, anti-affinity и PodDisruptionBudget на нагрузочном стенде. HPA Realtime учитывает соединения/память, workers — lag; глобальный FIFO не ускоряется простым увеличением числа selectors. Shutdown прекращает новые соединения и даёт ограниченное drain; процессные таймеры после рестарта восстанавливаются из DB.

Метрики и tracing по commandId/matchId/correlationId; userId не используется как label метрики. Нужны алерты outbox/inbox lag, due timer lag, session errors, DB saturation, потеря WS, reconnect rate и storage limits. TLS только на внешних границах ingress/egress по §2, внутренний HTTP/TCP без mTLS, внутренние credentials по сервисам, NetworkPolicy, закрытые internal APIs, секреты вне Git. Доверенные CA и сертификаты внешних TLS-соединений Kubernetes-окружения поступают из Vault через предусмотренную интеграцию; их проверка обязательна. Внутренний plaintext не обозначается как ошибка проверки сертификата. Backup/restore проверяется отдельно, без обещаний нулевого RPO при потере всей БД.

## Risks / Trade-offs

- [Отсутствие mTLS внутри mesh убирает шифрование и mesh identity] → Изолированная сеть, NetworkPolicy и прикладные credentials; не утверждать, что plaintext равнозначен защищённому каналу.
- [Game координирует участие всех сервисов] → Явный модуль участия, короткие транзакции и отдельные метрики; вынос требует последующего дизайна, не скрытого shared database.
- [Строгий FIFO сериализует выбор] → Benchmark отдельного queue_control, короткие операции; не заявлять линейное масштабирование.
- [Переходы между очередью/лобби и Game не атомарны между БД] → Durable operations, идемпотентные вызовы, CAS и reconciliation; неизвестный исход не освобождает игрока.
- [50k heartbeat/с и introspection могут стать основным bottleneck] → Измерять отдельно, пакетировать leases и touches с доказанным сохранением семантики; не вводить кеш отзыва сессии незаметно.
- [5 секунд на ход чувствительны к сети и перегрузке] → Серверный срок, видимый countdown, мониторинг и ограничение очередей; RTT не компенсируется автоматически.
- [Core NATS доставка до socket может потеряться] → Клиентские версии, ack и периодическая сверка snapshot; JetStream остаётся durable входом dispatcher.
- [Обрыв инфраструктуры может дать массовые поражения] → Отдельный fault test и runbook; изменение правил требует отдельного согласования.
- [Нет source code и измерений] → Пошаговые вертикальные срезы, сначала тесты инвариантов, затем масштабирование, без обещаний вместимости по одной схеме.

## Migration Plan

1. Зафиксировать контракты, версии toolchains, структуру и локальное окружение. Поднять изолированный стенд PostgreSQL/Redis/NATS.
2. Добавить versioned migrations каждого владельца данных, outbox/inbox и идемпотентность. Проверить чистую установку и повторный запуск миграций.
3. Последовательно включить Auth/participation, Lobby/Matchmaking, подготовку, Game, Realtime и три клиента; каждую стадию закрывать интеграционными сценариями.
4. Подготовить Kubernetes-кластер, перенести существующие credentials и TLS-материалы в Vault без потери данных, установить отдельные Kubernetes/Istio Helm charts из YAML и проверить миграцию стенда. Затем проверить backup/restore и отказ одного экземпляра, затем выполнить ступенчатые нагрузочные профили.
5. Изменения схемы и событий — expand/contract: сначала совместимое чтение и дополнительные поля, затем новые writers; destructive cleanup отдельным изменением. Rollback приложения допустим только при совместимой схеме.
6. При rollback остановить приём новых матчей, дождаться/контролируемо завершить текущие операции, сохранить БД, streams и offsets. Не удалять durable данные для восстановления сервиса. Публикация в публичную среду не входит в выполнение этого плана без отдельной авторизации.

- Ресурсный бюджет нагрузочного стенда, облако и конкретные версии мобильных ОС фиксируются в паспорте испытания; профили параметризуются.
