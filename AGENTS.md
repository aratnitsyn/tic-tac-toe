# Инструкции для работы с проектом

## Описание проекта

Учебная микросервисная платформа классических крестиков-ноликов для Web, iOS и Android. Целевая вместимость — 100 000 одновременно активных пользователей суммарно в меню, лобби, очереди и матчах; достижение цели требует нагрузочных испытаний.

Первая версия — только PvP: автоматический FIFO-подбор или приватное лобби на двух игроков с приглашением по коду. Предполагаемые сервисы: Auth, User, Lobby, Matchmaking, Game и Realtime.

В репозитории есть требования OpenSpec и независимо собираемые backend scaffold: пять Kotlin/Spring Boot приложений и два Go приложения с health endpoints. Есть локальный Compose стенд PostgreSQL/Redis/NATS с проверкой изоляции БД. Реализованы Auth API, защищённый Gateway и минимальный событийный User; сквозной logout ожидает Game, полнота отмечается в tasks.md. Остальные доменные API и Kubernetes/Istio инфраструктура пока не реализованы. Не описывайте scaffold как работающую игровую платформу.

## Технологический стек

Заданный стек для будущей реализации:

| Область | Технологии |
|---|---|
| Backend | Kotlin (JDK 25), Go |
| JVM framework | Spring Boot 3.5.x, последний стабильный patch; сейчас 3.5.16 |
| API gateway и безопасность | Spring Cloud API Gateway, Spring Security |
| Хранилище | PostgreSQL |
| Кеш | Redis |
| События | NATS JetStream |
| Маршрутизация и границы сети | Istio service mesh, отдельные ingress/egress gateway deployments |
| Оркестрация | Kubernetes |
| Web | TypeScript, React |
| iOS | Swift |
| Android | Kotlin |

Внешний API: HTTPS `/api/v1/**`; WebSocket: WSS `/wss`. TLS завершается на ingress gateway, внутри mesh используются HTTP/WS без application TLS и proxy mTLS; внутренние хранилища используют свои TCP-протоколы. Egress gateway устанавливает TLS к внешним HTTPS-системам. Не возвращайте требование TLS на каждом внутреннем участке и не добавляйте NGINX вторым ingress без отдельного решения.

Границы сервисов, распределение языков и маршруты определены в design.md. Версии backend закреплены в manifests: JDK 25, Kotlin 2.3.21, Spring Boot 3.5.16, Gradle Wrapper 9.8.1; Go 1.24.0. Изменения архитектуры сверяйте с дизайном.

## Структура проекта

```text
AGENTS.md                          # Общие инструкции для репозитория
README.md                          # Краткое описание проекта
.agents/skills/openspec-*/          # Локальные навыки OpenSpec
openspec/
  config.yaml                      # Конфигурация OpenSpec
  specs/                           # Основные спецификации; пока пусто
  changes/
    archive/                       # Архив изменений; пока пусто
    pvp-platform-v1/
      .openspec.yaml               # Метаданные изменения
      proposal.md                  # Объём, ограничения, открытые решения
      specs/<capability>/spec.md   # ФТ, НФТ и конечные автоматы
```

Текущий источник требований — `openspec/changes/pvp-platform-v1/`. Конечные автоматы находятся в `player-state-machine`, `match-state-machine` и `game-state-machine`. Основные спецификации `openspec/specs/` заполняются при последующем завершении соответствующего OpenSpec-процесса.

Сервисы расположены в services/{api-gateway,auth,user,lobby,game,matchmaking,realtime}; общие проверки — config/ и scripts/, backend CI — .github/workflows/backend.yml. Локальная инфраструктура находится в infra/local/, инструкция — docs/runbooks/local.md. Контракты находятся в contracts/, их структурная проверка — python3 tools/contracts/check-structure.py. Полная schema-validation отложена по указанию пользователя, устанавливать её npm-пакеты без нового разрешения не нужно. Клиенты и Kubernetes/Istio manifests ещё не созданы. При их появлении обновите структуру и команды в этом файле. Более локальные AGENTS.md уточняют правила для своих каталогов.

## Установка и запуск

Работайте из корня репозитория. Для работы с требованиями нужен доступный в PATH OpenSpec CLI; способ его установки и версию нужно документировать при настройке воспроизводимого окружения.

Доступные команды работы с требованиями:

```sh
openspec list --json
openspec list --specs --json
openspec status --change pvp-platform-v1 --json
openspec validate pvp-platform-v1 --strict
```

Команды scaffold из каталога соответствующего сервиса:

- Kotlin: `./gradlew clean build --no-daemon`, `./gradlew bootRun`; используйте JAVA_HOME для JDK 25. На macOS: `export JAVA_HOME="$(/usr/libexec/java_home -v 25)"`.
- Go: `go build -o build/<service> .`, `go run .`.
- Из корня: `scripts/install-go-tools.sh`, затем `scripts/check-go.sh`.

Auth/User/Gateway запускаются из корня через `python3 scripts/run-service.py <service>` после миграций и bootstrap streams; см. docs/runbooks/auth.md. Ключи и служебные credentials находятся в игнорируемом infra/local/secrets/, сохраняются при рестартах. Команд запуска полной игровой платформы пока нет. Не запускайте вымышленные `npm install`, Gradle, Docker Compose или Kubernetes-команды без соответствующих манифестов. Когда появятся исполняемые компоненты, добавьте точные проверенные команды, рабочие каталоги, версии инструментов и необходимые переменные окружения без секретных значений. Для существующих модулей используйте их wrappers, lock-файлы и документированный менеджер зависимостей.

## Правила кода, линтеры и стиль

JVM backend собирается и запускается на JDK 25 с JVM target 25. Используется последний стабильный Spring Boot только в ветке 3.5.x; текущая закреплённая версия — 3.5.16. Не используйте динамическую версию `3.5.+`: при обновлении проверяйте новый стабильный patch и закрепляйте точный номер во всех JVM-сервисах. Kotlin сейчас 2.3.21 для JVM 25. Требование JDK 25 относится к backend, не задаёт toolchain Android.

Базовый JVM-пакет и Gradle group: `com.github.aratnitsyn.tictactoe`. Пакет сервиса — база + имя сервиса: `auth`, `apigateway`, `user`, `lobby`, `game`; дефисы artifactId удаляются только в имени пакета (`api-gateway` → `apigateway`). ArtifactId соответствует имени сервиса в settings.gradle.kts. Исходники располагаются в соответствующем package каталоге. Для Go используется namespace модулей `github.com/aratnitsyn/tictactoe/services/<service>`; исполняемая точка входа сохраняет обязательный `package main`.

Для Kotlin scaffold настроены CLI ktlint 1.7.1 и detekt 1.23.8 в изолированных JAR, включённые в Gradle check/build; для Go — gofmt, go vet и golangci-lint 2.1.6. Прочие клиентские инструменты ниже пока только планируются:

- Kotlin: форматирование через ktlint, статический анализ через detekt. Имена типов — PascalCase, функций и свойств — camelCase. Checkstyle не применяется к Kotlin; при появлении Java настройте его отдельно для Java-исходников.
- Go: форматирование через gofmt, проверка через go vet; дополнительные проверки — golangci-lint после добавления конфигурации.
- TypeScript/React: строгая типизация, ESLint и Prettier. Не используйте `any` без обоснованной необходимости; компоненты именуйте в PascalCase.
- Swift: SwiftFormat и SwiftLint после добавления соответствующих конфигураций.
- При настройке каждого модуля закрепите совместимые версии инструментов, единые правила форматирования и команды проверки в сборке/CI. Не заявляйте прохождение ещё не настроенных проверок.
- Следуйте локальному стилю, избегайте несвязанных переформатирований и новых зависимостей без необходимости. Комментарии объясняют причины и ограничения.
- Изолируйте правила партии от транспорта и инфраструктуры. Проверяйте права, входные данные и допустимость переходов на сервере; клиентская проверка дополняет серверную.
- Обрабатывайте ошибки явно; не скрывайте сбои пустыми обработчиками. Не записывайте пароли, токены и другие секреты в код, логи или тестовые данные.
- Изменения конкурентной логики проверяйте на повтор команд, гонки, устаревшие версии и граничные моменты таймеров. Для проверок времени используйте управляемое время вместо длительных ожиданий.

## Ограничения и работа с требованиями

- Перед изменениями читайте релевантные спецификации, сценарии и открытые решения в proposal.md. Не подменяйте открытые вопросы собственными решениями без явного обозначения допущений.
- Используйте соответствующие локальные навыки OpenSpec для исследования, подготовки, изменения, реализации и архивирования change. В explore не реализуйте код; соблюдайте область действий, разрешённую пользователем.
- Не создавайте каталоги новых OpenSpec change вручную: используйте CLI. Не архивируйте и не синхронизируйте спецификации без соответствующего запроса.
- Не меняйте согласованное поведение ради удобства реализации. При изменении требований согласованно обновляйте затронутые спецификации и автоматы в рамках разрешённой задачи.
- Ключевые инварианты: одно состояние участия, один активный матч и одна активная сессия на аккаунт. Новый вход при активной сессии отклоняется; срок сессии — 24 часа бездействия.
- Партия: поле 3×3, случайное назначение X/O, первым ходит X, на ход 5 секунд. Готовность обоих — за 10 секунд, затем отсчёт 5 секунд; отключение во время отсчёта отменяет матч.
- Во время начавшейся партии отключение ставит игру на паузу. Запас восстановления — суммарно 30 секунд на каждого игрока за матч; остаток хода сохраняется. Точные результаты и возвраты игроков сверяйте со спецификациями.
- В первой версии нет PvE, Bot/AI worker, рейтингового подбора, выбора лимита хода, восстановления пароля, подтверждения email и входа через внешних провайдеров. Не добавляйте их попутно.
- Только вместимость 100 000 пользователей и согласованные игровые таймеры утверждены численно. Предварительные SLO в proposal.md не являются согласованными критериями приёмки.
- Не меняйте пользовательские правки вне задачи. Не выполняйте разрушительные операции, публикацию или развёртывание без соответствующей авторизации.

## Перед завершением задачи

1. Проверьте соответствие результата запросу, спецификациям и автоматам; обновите связанную документацию, если она затронута.
2. Для изменений OpenSpec выполните `openspec validate <change-name> --strict` и проверьте статус change. Не отмечайте незавершённые задачи выполненными.
3. Для кода выполните доступные форматтеры, линтеры, сборку и релевантные тесты затронутых модулей. Отсутствие инструмента или невозможность запуска явно укажите; не выдавайте это за успешную проверку.
4. Проверьте diff и новые файлы: нет ли секретов, случайных артефактов, несвязанных изменений и расхождений между контрактами. Для небольших изменений документации не создавайте искусственные тесты.
5. В итоговом ответе кратко опишите результат, изменённые файлы, выполненные проверки и оставшиеся ограничения. Не утверждайте достижение нагрузки или доступности без измерений.
