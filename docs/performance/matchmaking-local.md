# Локальный benchmark queue_control

Дата: 2026-10-18. Это измерение выбора/резервирования пары в PostgreSQL, без Game,
HTTP, NATS publish, Auth и клиентов. Целевая вместимость 100 000 этим не подтверждена.

Окружение: macOS Darwin arm64, Go 1.24.0, локальный Compose PostgreSQL
17.6-bookworm. Docker Desktop: 2 CPU, 2 066 595 840 байт RAM (~1,92 GiB) на весь
Docker engine; в нём также работают Redis/NATS. Отдельные CPU/RAM лимиты PostgreSQL
в Compose не заданы. Go selectors работают на хосте. Схема соответствует миграциям
V001–V003, заранее создано 400 AVAILABLE/connected tickets.

Воспроизведение из корня:

```sh
python3 scripts/benchmark-matchmaking.py
```

Скрипт загружает local.env/игнорируемые credentials, запускает отдельный Go-тест,
создаёт изолированную схему и удаляет её после проверки. Четыре конкурентных selector
выполняют 200 reservations (по 50 каждый), сохраняя pair operation, два RESERVED и
QueueChanged outbox в каждой транзакции. PostgreSQL RTT и ожидание queue_control
включены в latency. Проверяются число пар/участников и соседство выбранных FIFO-пар.

| Метрика | Измерение |
|---|---:|
| Время участка выбора | 0,934 с |
| Throughput | 214,12 пары/с |
| Selection p50 | 17,708 мс |
| Selection p95 | 25,009 мс |
| Selection max | 39,854 мс |
| Успешных samples pg_stat_activity | 461 |
| Сумма наблюдаемых ожидающих Lock | 1250 |
| Нарушения FIFO / повторное назначение ticket | 0 / 0 |

Sampler запрашивает pg_stat_activity примерно каждые 2 мс и считает только соединения
с application_name текущей тестовой схемы и запросом queue_control. 1250 — сумма
числа ожидающих по samples, а не число уникальных ожиданий и не миллисекунды. Значение
1250/461 ≈ 2,71 ожидающих соединения на sample показывает конкуренцию за глобальный
порядок при четырёх selectors. Sampler сам добавляет нагрузку, а короткий прогон не
измеряет длительное плато, p99 или насыщение полного сервиса.

Сериализованный участок действительно ограничивает выбор. Увеличение replicas не
обещает линейного роста, а SKIP LOCKED/шардирование не являются допустимым способом
объявить сохранение строгого FIFO. В runtime один цикл worker выбирает одну пару с
настраиваемым MATCHMAKING_RETRY_MS (локально 250 мс); частота worker и сетевые вызовы
дополнительно ограничивают фактическую скорость. Перед этапом нагрузочной приёмки
нужно измерить полный поток admission/AssignPair, backlog, настройки workers/pools,
ресурсы DB и длительное плато, а затем выполнить профили из design §10.

Отдельная проверка `scripts/check-matchmaking-runtime.py` подтвердила потерю ответа
после Game commit, restart, ручной replay исходного operationId, единственный матч,
сохранение FIFO и конфликт cancel после назначения. Это функциональное доказательство,
не результат нагрузочного испытания. Возврат после реальной отмены подготовки (6.5)
остаётся открытым до этапа 7.
