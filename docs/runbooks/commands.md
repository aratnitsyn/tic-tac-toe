# Идемпотентные команды

CommandStore в четырёх JVM и двух Go сервисах — инфраструктурный компонент,
пока не подключённый к HTTP handlers. Callback получает ту же транзакцию,
в которой сохраняется ответ. Не выполняйте необратимые сетевые действия внутри
callback: используйте transactional outbox.

Scope ключа: userId + operationType + commandId. PostgreSQL advisory transaction
lock сериализует повторы. Версии и доменные блокировки проверяет callback:
CommandStore не заменяет concurrency control партии или участия.

SHA-256 рассчитывается от JSON с сортировкой ключей объектов; порядок массивов
сохраняется. Другой payload того же ключа даёт IDEMPOTENCY_CONFLICT. Ответ и эффект
фиксируются одним commit; ошибка callback откатывает оба. При потере ответа
повторяется тот же commandId и возвращается сохранённый результат.

По умолчанию expires_at NULL: автоматического удаления нет. Это сохраняет
результаты матчей на весь жизненный цикл и превышает минимум 24 часа для остальных
операций. Сроки хранения и безопасная очистка требуют отдельной реализации.

Подготовка: запустить локальные хранилища и применить миграции каждого сервиса
по [migrations.md](migrations.md). Настоящие PostgreSQL integration tests:

```sh
export JAVA_HOME="$(/usr/libexec/java_home -v 25)"
python3 scripts/check-command-stores.py
```

Скрипт читает локальные credentials из игнорируемого .env без вывода их значений.
Он запускает четыре JVM набора и два Go набора с race detector.
Без PG_JDBC_URL / PG_DSN обычная сборка пропускает DB integration tests;
такой прогон не считается проверкой транзакционных гарантий.
