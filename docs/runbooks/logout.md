# Выход из аккаунта и очистка участия

## Протокол

`POST /api/v1/auth/logout` через Gateway принимает действующий token/cookie и
`Idempotency-Key`. Ответ `202` содержит `operationId` и `CLOSING` (либо `CLOSED`
при повторе уже завершённой операции). Это подтверждение сохранения операции,
а не обещание, что очистка Game уже закончилась. Web cookie удаляется в ответе;
фоновое завершение не требует присутствия клиента.

Auth одной транзакцией сохраняет `logout_operations` и переводит session slot
`ACTIVE → CLOSING`. В этом состоянии introspection и выдача/потребление WS ticket
не предоставляют доступ, новый login возвращает `SESSION_ALREADY_ACTIVE`.
Даже истечение прежнего `expires_at` не открывает вход из `CLOSING`.

Auth worker повторяет `POST /internal/v1/participation/logout` с исходными
`operationId`, `userId`, `sessionId` и своим служебным credential. Только ответ
`APPLIED` с совпадающим operationId позволяет одной транзакцией закрыть session
slot и отметить операцию завершённой. Тайм-аут, ошибка HTTP или неизвестный ответ
оставляют операцию незавершённой. После рестарта Auth читает те же операции из БД.
Повтор завершения проверяет sessionId и не закрывает новую сессию.

## Поведение Game

| Текущее состояние | Эффект выхода |
|---|---|
| MENU | Сохраняется MENU; версия увеличивается |
| QUEUED | MENU; Matchmaking получает ParticipationChanged и отменяет старый ticket |
| Ожидающее LOBBY | Удаляется место, закрывается регистрация комнаты, участие MENU |
| WAITING_READY / COUNTDOWN | Подготовка отменяется; выходящий MENU, подключённый соперник по источнику |
| X_TURN / O_TURN / PAUSED | SURRENDER: выходящий проиграл, соперник выиграл, оба MENU |
| Уже завершённая партия | Существующий результат остаётся неизменным |

Перед обработкой применяются наступившие сроки. Поэтому выход ровно в срок
хода сохраняет TURN_TIMEOUT; выход после срока отсчёта обрабатывается уже в
начавшейся партии. Выход до старта не создаёт игрового поражения.
При возврате соперника в очередь сохраняется originalSequence, при возврате
в лобби прежняя готовность сбрасывается и код ротируется.

Изменение Game/матча/участия, надёжных таймеров, результата команды LOGOUT и outbox
фиксируется одной транзакцией. Повтор исходной команды возвращает сохранённый
ответ и не затрагивает новое участие пользователя; изменённый payload с тем же
ключом отклоняется. Результат LOGOUT нельзя удалять, пока Auth может повторять
операцию. Токен сессии в этот результат не попадает.

Порядок блокировок: command → участники по userId → match → game.
MatchId сначала читается без одиночной блокировки участника, затем проверяется
под полным набором блокировок. Если участие перешло в другой матч, обработка
повторяется в новой транзакции. Незавершённая coordination operation даёт `503`,
а не фиктивный `APPLIED`: coordination worker должен сначала установить её исход.
Версия увеличивается даже при выходе из MENU, чтобы запрос с прежней
expectedVersion не мог поздно занять лобби/очередь после выхода.

Закрытие проекций асинхронное. Lobby consumer `lobby-menu-v1` обрабатывает
ParticipationChanged через inbox, проверяет текущее участие в Game и ждёт
завершения локальных room operations. Старое MENU-событие не закрывает комнату, которой игрок всё ещё владеет.
Если игрок уже занял другое лобби, старый код закрывается; новое участие
не изменяется. Формирование пары защищено pending room operation и статусом PREPARING. Consumer `lobby-return-v1` продолжает
обрабатывать отмены подготовки. Matchmaking использует существующий consumer
ParticipationChanged с проверкой текущего участия и версии ticket.
До обновления проекции старый код комнаты всё равно не создаёт матч: Game уже
закрыл регистрацию. Межсервисного SQL из приложений нет.

## Восстановление

При зависшем `CLOSING` проверьте сохранённую операцию в **Auth**, доступность
внутреннего HTTP Game и credential, Game DB/блокировки, pending coordination
operations и логи workers. Для идентификации используйте operationId; token и
credential не записывайте в диагностические сообщения.

Если Game уже выполнил выход, а Auth не получил ответ, восстановите связь и
дождитесь повторного POST с **тем же** operationId. Game вернёт сохранённый
результат. Если операция координации ещё PENDING, восстановите её worker;
не освобождайте участие по возрасту операции. Lag Lobby/Matchmaking проверяйте
по outbox/inbox и durable consumers; инструкции повторной доставки — в
[events.md](events.md).

Не переводите CLOSING вручную в CLOSED, не удаляйте session slot, command result,
participation или RESERVED ticket ради возможности войти. Это обходит координацию
и ограничение одной сессии. Не создавайте новый operationId для неизвестного
исхода старого выхода.

При утрате token **без явного выхода** штатный путь — дождаться 24 часов
бездействия с момента последнего авторизованного обращения. Heartbeat тоже
продлевает активность. В v1 нет восстановления пароля, принудительного входа,
замены активной сессии другим устройством или операторского обхода этого правила.
Потеря соединения сама по себе не является logout.

## Проверки

После запуска локальных PostgreSQL/Redis/NATS, миграций и bootstrap streams:

```sh
export JAVA_HOME="$(/usr/libexec/java_home -v 25)"
python3 scripts/check-command-stores.py --only kotlin --service game
python3 scripts/check-command-stores.py --only kotlin --service auth
python3 scripts/check-command-stores.py --only kotlin --service lobby
python3 scripts/check-logout-runtime.py
python3 -m unittest discover -s scripts/tests -v
```

Для runtime smoke также нужны собранные Gateway и Go binary
`services/matchmaking/build/matchmaking`; команды — в
[preparation.md](preparation.md). Скрипт использует случайные порты 127.0.0.1,
создаёт тестовые аккаунты/матчи и сохраняет их для разбора. Останавливает только
свои процессы; инфраструктуру и данные не удаляет. В тесте proxy теряет ответы
Game после commit, Auth получает SIGKILL и восстанавливает исходную операцию.
Обычные сценарии не отключают production rate limiter. Selector Matchmaking
в этом smoke отложен на час, чтобы одиночный тестовый ticket не попал в пару
с сохранёнными чужими tickets; HTTP admission и NATS consumers работают.

Проверки не подтверждают 100 000 пользователей, Kubernetes/Istio TLS или закрытие
живого WSS-соединения: Realtime и его проверка сессий реализуются на этапе 10.
